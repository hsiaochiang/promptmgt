# Feature Specification: 專案導向提示詞管理應用

**Feature Branch**: `001-prompt-management-app`  
**Created**: 2025-12-19  
**Status**: Draft  
**Input**: User description: "建立一個專為個人打造的「專案導向」提示詞管理桌面應用程式。目標是透過低摩擦的草稿機制、結構化的專案分類、以及 Markdown 檔案管理，解決提示詞分散、難以查找與版本混亂的問題，並提供一個舒適的撰寫與整理環境。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 快速草稿捕捉 (Priority: P1)

使用者需要快速記錄突然出現的提示詞靈感，無需立即決定分類或完善內容。使用者打開應用程式後，可立即在「收件匣」中開始輸入想法，系統自動儲存以防止遺失。當使用者準備好時，可將草稿「轉正」為正式提示詞，指定所屬專案、添加標籤和設定狀態。

**Why this priority**: 這是核心價值主張 - 降低創建摩擦。如果用戶無法快速捕捉想法，整個系統的價值就會大打折扣。這是 MVP 的基礎功能。

**Independent Test**: 可透過「開啟應用 → 輸入文字 → 關閉 → 重新打開」來驗證自動儲存功能，並透過「將草稿歸檔至專案」來驗證轉正流程，完全不依賴其他功能。

**Acceptance Scenarios**:

1. **Given** 使用者打開應用程式且收件匣為空，**When** 使用者開始輸入文字，**Then** 文字內容被即時自動儲存，即使未手動保存
2. **Given** 收件匣中有一個草稿，**When** 使用者點擊「歸檔」並選擇目標專案、輸入標題、添加標籤，**Then** 草稿從收件匣移除，在目標專案中創建新的提示詞檔案
3. **Given** 使用者正在編輯收件匣草稿，**When** 應用程式意外關閉，**Then** 重新打開後草稿內容完整保留
4. **Given** 收件匣中有多個草稿，**When** 使用者查看收件匣列表，**Then** 草稿按最後編輯時間排序顯示，每個草稿顯示前 50 字預覽

---

### User Story 2 - 專案分類管理 (Priority: P2)

使用者需要將提示詞按業務目標或客戶進行群組管理。使用者可創建專案（如「客戶A專案」、「內部工具開發」），每個專案包含相關的提示詞文件。使用者可設定專案狀態（進行中/已結案/暫停/規劃中）以在儀表板上區分活躍與歸檔項目。

**Why this priority**: 提供結構化組織能力，解決「提示詞分散」問題。這是在基礎捕捉功能之上的組織層，讓系統從單純的筆記工具升級為專案管理工具。

**Independent Test**: 可獨立測試「創建專案 → 添加提示詞 → 切換狀態 → 查看專案列表」流程，不需要其他高級功能如標籤或搜尋。

**Acceptance Scenarios**:

1. **Given** 使用者在專案管理介面，**When** 使用者點擊「新增專案」並輸入名稱和描述，**Then** 新專案出現在列表中，預設狀態為「規劃中」
2. **Given** 專案列表中有多個專案，**When** 使用者切換專案狀態為「已結案」，**Then** 該專案在主儀表板的「進行中」區域消失，移至「已結案」區域
3. **Given** 使用者在專案內部，**When** 使用者創建新提示詞或歸檔草稿，**Then** 提示詞與專案關聯，存儲在專案對應的檔案路徑下
4. **Given** 使用者查看儀表板，**When** 載入頁面，**Then** 「進行中」專案優先顯示，每個專案顯示提示詞數量和最後更新時間

---

### User Story 3 - Markdown 編輯與複製 (Priority: P1)

使用者需要使用熟悉的 Markdown 語法撰寫提示詞，並能快速複製內容至 AI 工具（如 ChatGPT、Claude）。編輯器支援語法高亮，提升撰寫體驗。使用者可選擇「完整複製」（包含元數據）或「僅複製內容」（去除標題、標籤等元數據，僅保留提示詞本體）。

**Why this priority**: 編輯和使用提示詞是核心工作流程。好的編輯體驗直接影響用戶滿意度，而一鍵複製功能是「降低摩擦」目標的關鍵實現。

**Independent Test**: 可透過「打開提示詞 → 編輯內容 → 預覽 Markdown → 複製」來獨立驗證，不依賴專案管理或標籤系統。

**Acceptance Scenarios**:

1. **Given** 使用者打開提示詞編輯器，**When** 使用者輸入 Markdown 語法（如標題、列表、程式碼區塊），**Then** 編輯器即時顯示語法高亮，預覽區正確渲染格式
2. **Given** 使用者編輯完提示詞，**When** 使用者點擊「僅複製內容」按鈕，**Then** 系統將提示詞本體（去除 YAML front matter 和標題等元數據）複製到剪貼簿，並顯示「已複製」提示
3. **Given** 使用者查看提示詞，**When** 使用者點擊「完整複製」按鈕，**Then** 系統複製包含元數據的完整內容到剪貼簿
4. **Given** 使用者在編輯器中，**When** 使用者使用快捷鍵 Ctrl+S（或 Cmd+S），**Then** 系統保存當前內容並顯示保存成功提示

---

### User Story 4 - 片語庫與快速插入 (Priority: P3)

使用者需要維護常用的提示詞片段（如角色設定、輸出格式要求、限制條件），並在編輯時快速插入。使用者可創建片語、分類管理，並在編輯器中透過點擊或搜尋將片語插入到游標位置。系統追蹤片語使用次數，幫助使用者了解哪些模組最常被使用。

**Why this priority**: 這是效率提升功能，但不是核心 MVP。用戶可以先手動複製貼上，此功能可在基礎系統穩定後再添加。

**Independent Test**: 可透過「創建片語 → 打開編輯器 → 搜尋並插入片語 → 查看使用統計」來獨立測試，不影響其他核心功能。

**Acceptance Scenarios**:

1. **Given** 使用者在片語管理介面，**When** 使用者創建新片語並指定名稱、分類和內容，**Then** 片語被保存並出現在片語庫列表中
2. **Given** 使用者在編輯器中撰寫提示詞，**When** 使用者打開片語面板並點擊某個片語，**Then** 片語內容被插入到當前游標位置
3. **Given** 使用者在編輯器中，**When** 使用者在片語面板搜尋框輸入關鍵字（如「RAG」），**Then** 面板僅顯示匹配的片語項目
4. **Given** 使用者查看片語庫，**When** 使用者查看片語詳情，**Then** 系統顯示該片語的使用次數和最後使用時間

---

### User Story 5 - 標籤與搜尋 (Priority: P2)

使用者需要透過標籤跨專案篩選提示詞（如找出所有標記為「RAG」或「產碼」的提示詞），並能進行全文搜尋。使用者可為提示詞添加多個標籤,透過標籤過濾器快速定位內容。全文搜尋功能同時搜尋標題、內容和標籤，並高亮匹配結果。

**Why this priority**: 解決「難以查找」問題的核心功能。在提示詞數量增加後，此功能變得至關重要，但在初期少量提示詞時可透過瀏覽專案來管理。

**Independent Test**: 可透過「創建多個提示詞並添加標籤 → 使用標籤過濾 → 使用搜尋功能」來獨立驗證，不依賴片語或版本控制功能。

**Acceptance Scenarios**:

1. **Given** 使用者在提示詞編輯介面，**When** 使用者輸入標籤（如「RAG」、「文案」），**Then** 標籤被添加到提示詞元數據，並在提示詞列表中顯示
2. **Given** 使用者在儀表板或專案視圖，**When** 使用者選擇一個或多個標籤過濾器，**Then** 列表僅顯示包含所選標籤的提示詞（跨所有專案）
3. **Given** 使用者在搜尋框輸入關鍵字，**When** 使用者按下 Enter 或點擊搜尋按鈕，**Then** 系統返回標題、內容或標籤中包含該關鍵字的所有提示詞，並高亮匹配文字
4. **Given** 使用者查看儀表板，**When** 載入頁面，**Then** 儀表板顯示「最近編輯」列表（最近 5 個修改的提示詞）和「待整理草稿」數量

---

### User Story 6 - 本地檔案管理與版本歷史 (Priority: P3)

使用者希望所有數據以標準 Markdown 格式存儲在本地檔案系統，不依賴專有格式，可隨時用其他工具存取。系統能讀取並顯示檔案的修改歷史（若用戶使用 Git 等版本控制），使用者可查看提示詞的變更歷史並回溯到先前版本。

**Why this priority**: 這是差異化特性（數據所有權、開放格式），但不是啟動核心功能。初期版本可僅支援檔案讀寫，版本控制整合可後續添加。

**Independent Test**: 可透過「創建提示詞 → 在檔案系統中檢查檔案 → 用外部編輯器修改 → 在應用中刷新」來驗證檔案格式；版本歷史可獨立透過「查看歷史 → 選擇版本 → 對比差異」測試。

**Acceptance Scenarios**:

1. **Given** 使用者創建或編輯提示詞，**When** 使用者保存變更，**Then** 系統在專案對應的檔案路徑下創建或更新 Markdown 檔案，包含 YAML front matter（元數據）和內容本體
2. **Given** 使用者在檔案系統中直接編輯 Markdown 檔案，**When** 使用者在應用中刷新或重新打開專案，**Then** 應用讀取最新檔案內容並正確顯示
3. **Given** 提示詞檔案在 Git 版本控制下，**When** 使用者點擊「查看歷史」，**Then** 應用顯示該檔案的提交歷史列表（提交訊息、時間、作者）
4. **Given** 使用者查看提示詞的歷史版本，**When** 使用者選擇某個歷史版本，**Then** 應用顯示該版本內容，並提供「對比當前版本」和「恢復到此版本」選項

---

### Edge Cases

- **當使用者在收件匣中有超過 100 個未歸檔草稿時**：系統應分頁顯示或提供搜尋過濾功能，避免介面過載；顯示警告提示使用者整理草稿
- **當專案資料夾被外部工具刪除或移動時**：應用重新載入時應檢測檔案路徑變更，顯示錯誤訊息並提供「重新定位」或「移除損壞專案」選項
- **當提示詞檔案格式損壞（無效 YAML front matter）時**：系統應嘗試解析內容，降級顯示為純文字，並標記檔案為「需要修復」
- **當兩個片語名稱重複時**：系統在創建時檢查重複，提示使用者重命名或合併
- **當使用者嘗試將草稿歸檔到不存在的專案時**：系統驗證專案存在性，若不存在則阻止操作並提示錯誤
- **當搜尋關鍵字返回超過 1000 個結果時**：系統限制顯示前 1000 個結果，並提示使用者細化搜尋條件
- **當使用者在編輯器中貼上大量文字（超過 100KB）時**：系統應顯示載入指示器，確保不會凍結介面
- **當提示詞標題包含檔案系統不允許的字元（如 `/` `\` `:` 等）時**：系統自動將特殊字元替換為安全字元（如 `-`），並向使用者顯示實際儲存的檔案名稱

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須提供「收件匣」工作區，允許使用者創建和編輯草稿而無需指定專案或元數據
- **FR-002**: 系統必須在使用者輸入時自動儲存草稿內容，無需手動保存操作
- **FR-003**: 系統必須允許使用者將草稿「轉正」為正式提示詞，包括選擇專案、輸入標題、添加標籤、設定狀態的流程
- **FR-004**: 系統必須支援創建和管理專案，每個專案包含名稱、描述、狀態（規劃中/進行中/已結案/暫停）、關聯檔案路徑
- **FR-005**: 系統必須將每個提示詞儲存為獨立的 Markdown 檔案，隸屬於特定專案的檔案路徑
- **FR-006**: 系統必須在提示詞檔案中使用 YAML front matter 儲存元數據（標題、專案、類型、狀態、標籤、目標模型、備註）
- **FR-007**: 系統必須提供 Markdown 編輯器，支援語法高亮和即時預覽
- **FR-008**: 系統必須提供兩種複製功能：「完整複製」（包含元數據）和「僅複製內容」（去除 front matter，僅保留內容本體）
- **FR-009**: 系統必須支援創建和管理片語（Snippets），包括名稱、分類、內容屬性
- **FR-010**: 系統必須允許使用者在編輯器中搜尋並插入片語到游標位置
- **FR-011**: 系統必須追蹤每個片語的使用次數和最後使用時間
- **FR-012**: 系統必須支援為提示詞添加多個標籤，並提供跨專案的標籤過濾功能
- **FR-013**: 系統必須提供全文搜尋功能，搜尋範圍包括提示詞標題、內容和標籤
- **FR-014**: 系統必須在搜尋結果中高亮匹配的關鍵字
- **FR-015**: 系統必須在儀表板顯示「最近編輯」提示詞列表和「待整理草稿」數量
- **FR-016**: 系統必須檢測提示詞檔案所在的版本控制系統（如 Git），並讀取檔案的提交歷史
- **FR-017**: 系統必須允許使用者查看提示詞的歷史版本，並提供對比和恢復功能
- **FR-018**: 系統必須驗證提示詞標題的字元合法性，自動替換檔案系統不允許的特殊字元
- **FR-019**: 系統必須在專案資料夾路徑無效時顯示錯誤訊息，並提供修復選項
- **FR-020**: 系統必須支援讀取和顯示外部工具直接編輯的 Markdown 檔案，確保雙向相容性
- **FR-021**: 系統必須在載入損壞的 YAML front matter 時降級為純文字顯示，並標記檔案狀態
- **FR-022**: 系統必須在片語名稱重複時阻止創建，並提示使用者重命名
- **FR-023**: 系統必須限制搜尋結果顯示數量（最多 1000 個），並在超過時提示細化搜尋
- **FR-024**: 系統必須在使用者貼上大量文字時顯示載入指示器，避免介面凍結

### Key Entities

- **Project（專案）**: 代表業務目標或客戶群組，包含名稱、描述、狀態（規劃中/進行中/已結案/暫停）、關聯檔案路徑、建立時間、最後更新時間。一個專案包含多個提示詞。
- **Prompt（提示詞）**: 最小運作單位，對應一個 Markdown 檔案，包含標題、所屬專案參考、類型（角色設定/產碼/文案/RAG 調教/結構分析）、狀態（Draft/Stable/Deprecated）、標籤、目標模型、內容本體、備註。
- **Snippet（片語）**: 可重複使用的文字區塊，包含名稱、分類（角色/格式/限制/語氣）、內容、使用次數、最後使用時間。
- **Draft（草稿）**: 收件匣中的臨時提示詞，包含內容本體、創建時間、最後編輯時間。草稿轉正後成為 Prompt。
- **Tag（標籤）**: 用於跨專案分類的關鍵字，如「RAG」、「產碼」、「文案」。多個提示詞可共享同一標籤。
- **Version History（版本歷史）**: 提示詞檔案的變更記錄，包含提交訊息、時間戳、作者、檔案差異（基於版本控制系統如 Git）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者可在 5 秒內從打開應用到開始記錄草稿（衡量「低摩擦」目標）
- **SC-002**: 使用者可在 30 秒內將草稿轉正為正式提示詞並歸檔到專案（衡量工作流程效率）
- **SC-003**: 使用者可在 10 秒內透過標籤或搜尋找到目標提示詞（衡量「解決難以查找」問題）
- **SC-004**: 使用者可在 3 秒內複製提示詞內容並貼上到 AI 工具（衡量使用便利性）
- **SC-005**: 系統在使用者編輯時每 3 秒自動儲存一次，防止數據遺失（衡量可靠性）
- **SC-006**: 當提示詞檔案被外部工具修改後，系統可在 5 秒內刷新並正確顯示最新內容（衡量雙向相容性）
- **SC-007**: 使用者可在 15 秒內創建片語並在編輯器中插入使用（衡量片語庫效率）
- **SC-008**: 全文搜尋在包含 1000 個提示詞的資料庫中返回結果的時間少於 2 秒（衡量效能）
- **SC-009**: 系統在啟動時載入包含 50 個專案和 500 個提示詞的資料的時間少於 5 秒（衡量啟動效能）
- **SC-010**: 使用者完成首次使用（創建專案 → 創建草稿 → 歸檔 → 複製）的成功率達 90%（衡量易用性）
- **SC-011**: 使用者報告的「因介面卡頓而中斷工作流程」事件低於 5%（衡量使用體驗）
- **SC-012**: 儲存的 Markdown 檔案可被至少 3 種主流 Markdown 編輯器（如 VS Code、Obsidian、Typora）正確開啟和編輯（衡量開放格式目標）

## Assumptions

- 假設使用者已熟悉 Markdown 語法，或願意學習基礎語法（標題、列表、程式碼區塊）
- 假設使用者的本地檔案系統允許應用程式讀寫檔案，且有足夠的儲存空間（至少 100MB）
- 假設桌面應用程式運行環境支援現代 Web 技術（如 Electron、Tauri 等框架）
- 假設使用者的作業系統為 Windows、macOS 或 Linux 主流版本
- 假設使用者不需要多裝置同步功能（本地單機使用），若需要可透過雲端硬碟（如 Dropbox、OneDrive）手動同步檔案資料夾
- 假設專案數量不超過 100 個，單一專案內提示詞數量不超過 500 個（效能優化的基準）
- 假設片語庫的片語數量不超過 200 個（效能優化的基準）
- 假設使用者若需要版本控制功能，已在專案資料夾初始化 Git 倉庫（系統僅讀取，不主動管理 Git 操作）
- 假設提示詞的平均長度為 500-2000 字，極端情況不超過 10,000 字
- 假設使用者主要使用場景為「個人使用」，不涉及多人協作或權限管理
- 假設使用者期望的「舒適撰寫環境」包括語法高亮、自動儲存、快速複製，但不強制要求所見即所得（WYSIWYG）編輯器

## Out of Scope

- 多裝置自動同步功能（使用者可透過第三方雲端服務手動同步檔案資料夾）
- 多使用者協作與權限管理
- 內建 AI 模型呼叫或測試功能（使用者需手動複製到外部 AI 工具）
- 提示詞效能分析或 A/B 測試功能
- 版本控制系統的主動管理（如自動提交、推送），僅支援讀取現有歷史
- 所見即所得（WYSIWYG）的 Markdown 編輯器，僅提供語法高亮和預覽
- 雲端儲存或資料庫後端，所有數據僅存儲在本地檔案系統
- 自動標籤建議或 AI 輔助分類功能
- 複雜的專案依賴關係或甘特圖等專案管理功能
- 加密或密碼保護功能（假設使用者在安全的本地環境使用）
- 跨平台之外的特殊裝置支援（如手機、平板、Web 版本）
- 匯入匯出功能（除了標準 Markdown 檔案讀寫外的其他格式，如 JSON、CSV）
